# Building and testing

## Linux and the common setup

With Nix, `nix develop` opens a shell with the toolchain and libraries (Rust, FFmpeg, libclang,
pkg-config, the Linux capture libraries or Swift and the macOS SDK, Node.js and pnpm). The build inside
it is the regular one below; the flake defines no package of its own. Intel macOS lacks a Swift 6
package in the pinned nixpkgs.

Linux (Debian/Ubuntu package names; FFmpeg 9 headers, tested with 9.0.2):

```sh
sudo apt install build-essential pkg-config libclang-dev \
    libavcodec-dev libavfilter-dev libavformat-dev libavutil-dev libdrm-dev \
    libpipewire-0.3-dev libspa-0.2-dev
cargo build --release                       # → target/release/eyepiece-pc
cargo build --release -p eyepiece-pc        # the CLI only
cargo build --release --no-default-features --features x11   # without PipeWire capture (no libpipewire needed)
cargo test
```

The FFmpeg bindings are generated by bindgen against the installed headers. Without the
`-dev` packages, set `FFMPEG_INCLUDE_DIR` / `FFMPEG_LIB_DIR` (see [env-local.sh](../../env-local.sh)
for headers unpacked from the `.deb`s), and `LIBCLANG_PATH` if libclang is not found.

Linux builds the CLI with KMS, X11 and (by default) PipeWire capture. See
[installation](../install.md#linux-kms-capture-permissions) for the capability KMS capture needs.

## Windows

Install LLVM (for libclang), unpack a BtbN FFmpeg 9 *shared* build
(`ffmpeg-n9.0-latest-win64-gpl-shared-9.0.zip`), then

```pwsh
$env:FFMPEG_INCLUDE_DIR = "C:\ffmpeg\include"; $env:FFMPEG_LIB_DIR = "C:\ffmpeg\lib"
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
cargo build --release      # put C:\ffmpeg\bin (the DLLs) on PATH or next to the .exe
```

The Windows (DXGI) path builds in CI but has never been run.

## Tests

```sh
cargo test                                   # Rust unit and integration tests
(cd web && pnpm check && pnpm test)          # web type check and unit tests
```

The suite does not touch a device or capture the screen. Tests that need hardware are `#[ignore]`d.

### Bridge interoperability tests

The nanopb/prost interop tests require a checkout of tinkerglass (the PC Display bridge), nanopb 0.4.9.1
source in `NANOPB_DIR`, `protoc`, `protoc-gen-nanopb`, a C compiler and Cargo:

```sh
bridge=../tinkerglass/mods/pcdisplay/bridge
out=target/bridge-interop
mkdir -p "$out"
PYTHONPATH="${NANOPB_PYTHONPATH:-}${PYTHONPATH:+:$PYTHONPATH}" \
  protoc -I contract --nanopb_out="-f$bridge/nanopb.options:$out" contract/eyepiece-rpc.proto
cc -std=gnu11 -I "$out" -I "$NANOPB_DIR" "$bridge/tests/wire_interop.c" "$bridge/wire.c" \
  "$out/eyepiece-rpc.pb.c" "$NANOPB_DIR/pb_common.c" "$NANOPB_DIR/pb_encode.c" \
  "$NANOPB_DIR/pb_decode.c" -o "$out/wire_interop"
EYEPIECE_WIRE_INTEROP="$out/wire_interop" cargo test -p eyepiece-link --test bridge_interop -- --ignored
```

The bridge's own protocol tests (configuration sequence, invalid video, nanopb wire format) live in the tinkerglass
repository under `mods/pcdisplay/bridge/tests/`; they build the host bridge
(`build.sh host`, `pcdisplay_bridge_host`) and drive it with `-N -H -1` as a null-decoder protocol bridge.

### Hardware tests

The `#[ignore]`d regression `session::tests::device_pane_reconfiguration` exercises pane moves, resizes,
packed alpha, fullscreen and PiP transitions, opacity acknowledgements, resumed frame reports and
reconnect against a real bridge. Run it only with stationary goggles, never while flying; see
[transports](../transports.md#hardware-regression-test).

## CI

`.github/workflows/ci.yml` builds and tests on Linux (Debian testing, FFmpeg 9), Windows and macOS, and
packages tar.gz, AppImage, zip and DMG releases.

## Packaging

`packaging/linux/build-appimage.sh` builds an AppImage containing the CLI. It needs
[linuxdeploy](https://github.com/linuxdeploy/linuxdeploy); without it the script stops after
assembling the AppDir. For a portable AppImage, build FFmpeg on an old base first with
`packaging/linux/build-ffmpeg.sh PREFIX` and point `FFMPEG_INCLUDE_DIR`, `FFMPEG_LIB_DIR` and
`LD_LIBRARY_PATH` at it (this is what CI does on Ubuntu 24.04). `packaging/linux/build-appimage-docker.sh` runs
exactly that in an `ubuntu:24.04` container (needs only docker or podman). It bundles the FFmpeg libraries but takes glibc, the GPU driver
stack (libva, libvdpau, NVIDIA/CUDA, OpenCL, Vulkan, GL), libdrm and PipeWire from the host.
An AppImage cannot carry file capabilities, so KMS capture does not
work from it (use PipeWire or X11 capture, or a native install with `setcap`).
